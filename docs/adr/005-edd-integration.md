# ADR-005：评估层集成 — 运行时指标由进程内采集，脚本只消费快照

> ADR 编号：`ADR-005` ｜ 状态：`已实现`（**落点已变**，见下方①）
> 创建 2026-08-14 ｜ 决策者 @devuser
>
> ① 落地时采集器在 `app/edc/`，现迁到 **`app/eval/edc/`**；`.agent/eval/` / `.agent/loop/`
> 那套外部脚本**已不在本仓**。读本文时把路径换成现在的落点，其余决策理由仍然成立。

## 1. 背景

评估层最初只是 `.agent/eval/` 与 `.agent/loop/` 下的一套独立 Python 脚本，
与应用运行时数据割裂：agent 调用指标（trace JSONL）和健康巡检产出要靠人工或心跳触发才汇总，
脚本拿不到运行时第一手数据，口径分散、基线无法闭环。

历史教训：2026-07-30 基线单日约 450 万 token，此前 cron 任务一度造成
**约 1 亿 token / 夜** 的消耗——没有度量就没有优化。

## 2. 决策考虑

- **触发因素**：评估层与运行时数据割裂；token 消耗失控教训。
- **约束条件**：采集与聚合必须零 LLM 消耗；沿用已有脚本工具链避免推倒重来；
  不改对外契约；Windows 可运行。
- **非目标**：不做独立托管可观测平台；不引入分布式链路追踪；不评估业务语义质量。

## 3. 决策选项

### 选项 A：纯脚本工具链（保持割裂，心跳触发）

- **优点**：零改造；采集逻辑集中在一个入口。
- **缺点与代价**：脚本直接依赖日志文件格式，字段变更会**静默破坏采集**；
  运行时指标无人周期生成，依赖心跳是否按时触发；口径在脚本与运行时各一份，无法保证一致。
- **适用场景**：评估是低频偶发动作、无需实时快照。

### 选项 B：运行时原生采集器 + 快照桥接（脚本只消费快照）

- **描述**：进程内提供 `EDCMetricsCollector`，由 `main.py` 周期调用 `collect(days=1)`
  聚合 trace 与健康巡检产出，写统一快照 `metrics.json`；脚本只读快照做分析、基线追踪与建议回流。
- **优点**：口径唯一；进程活着数据就在，不依赖心跳；全链路零 LLM（LLM 只出现在分析/优化阶段）；
  与已有基线机制（`--track-baseline` / `--diff`）无缝衔接。
- **缺点与代价**：多一个模块 + 周期接线；快照是单文件周期覆盖写，跨日历史要靠基线承担；
  数据源缺失时快照为空，需优雅降级。
- **适用场景**：评估是持续闭环、需要运行时第一手指标、且与既有脚本并存。

### 选项 C：独立可观测服务 / 托管平台

- **优点**：指标体系完整、可查询、可告警。
- **缺点与代价**：外部依赖与部署负担远超单机 Bot 的运维体量；与既有脚本链需额外适配层。
- **适用场景**：多实例、多服务大规模部署。

### 选项 D：不做（维持无闭环现状）

- **缺点与代价**：token 失控无法被系统化发现，优化建议永远滞后，评估层形同虚设。不可接受。

## 4. 决策结论

**选定：选项 B。**

- **核心理由**：① 口径唯一、可回溯，消除脚本侧重复解析导致的静默漂移；
  ② 采集纯 Python 零 LLM，基线可量化 token 消耗，直接回应「无度量就无优化」；
  ③ 复用既有基线机制，接入成本最低。
- **放弃其他选项**：A 口径两份且依赖心跳；C 超出单机运维体量；D 不可接受。
- **影响范围**：新增采集模块与周期接线；快照文件为新产物；既有分析脚本改为只读快照。

## 5. 后果

**正面**：评估闭环真实打通（指标 → 快照 → 分析/基线 → 建议回流）；token 有硬基线，
异常暴涨可通过 diff 及时发现；评估层常驻但零增量 LLM 成本。

**负面 / 需接受**：
- 多一个模块与周期任务，弃用时要一并移除接线（回滚成本可控，都是新增代码）。
- 快照是进程内周期覆盖写，依赖主进程常驻；单文件不留历史，跨日趋势只能靠两条基线对比。
- **数据源随 adr-006 迁移而变**：dsh 链路的指标在会话事件流里，
  `logs/agents/` 的路由字段（confidence / demoted）在新链路下不再产生——
  **R10 迁移完成前，本 ADR 的采集口径只对回切链路成立**。

**必须配套的约束**：
1. 指标只由采集器统一聚合，消费方**禁止**自己解析原始日志（否则口径立刻分叉）。
2. 重算快照不得改写既有链路追踪日志（只读）。
3. 采集与聚合阶段禁止调 LLM（纯 Python），LLM 只允许出现在分析与优化环节。
4. 数据源缺失时优雅降级为 `no_data` / 空统计，不给进程报警、不崩溃。
5. 单文件快照**不是**长期历史存储，历史回溯只走基线与按日归档。
