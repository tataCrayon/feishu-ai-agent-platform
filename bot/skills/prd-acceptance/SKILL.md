# 验收可测 + 待确认归零

两条都是**硬门**：任意一条不过，这份 PRD 就不能说「可实现、无待确认」。

## 1. 待确认归零（最重要）

扫描全文这些标记，一处都不许留：

`待确认 / 待定 / 待补充 / 待拍板 / TBD / TODO / ？ / ？? / 后续确认 / 暂定 / 待沟通 / 看情况`

判据：

- **每一处都必须给出处置**：要么补齐内容，要么删掉该条，要么明确写出「由谁在什么时候前定」。
- `- [ ] 待补充：…` 这类待办项同样算（去掉勾选框也算未完成）。
- 「按产品配置」「以实际为准」这类**没有指向具体配置项**的表述，等同于待确认。
- 全文通过判据：`待确认项 = 0`。做不到 0 就必须列出剩余清单与 owner。

## 2. 验收可测

每条功能条款必须能写出一句可观察断言：

> `[用户看到] 当 <条件> 时，<界面/接口> 表现为 <具体结果>`

不合格的表述（逐条给出改写建议）：

| 不合格 | 为什么 | 改成 |
|---|---|---|
| 体验流畅 / 及时到账 / 尽快 | 无判据 | 「提交后 ≤ 3s 弹出提交成功弹窗」 |
| 正常展示 / 正确显示 | 没说正常是什么 | 「展示 X / Y / Z 三列，空值显示 --」 |
| 支持多种币种 | 没列全 | 「支持 USDT / USDC / HKDAP，取自产品库币种枚举」 |
| 异常时提示 | 没说提示什么 | 「提示「该产品当前暂停申购或已下架」，不跳转」 |

同时检查：

- 每个成功路径有没有对应失败路径的可观察表现；
- 导出的文件（Excel/PDF）有没有字段清单与命名规则；
- 数值展示有没有格式规则（千分位、精度、单位空格）。

## 3. 输出

分两类回报：

1. **阻断清单**：每条 `待确认项` 与 `不可测条款`，带原文引用与章节。
2. **判定行**（原样给出，不要改写）：
   - `✅ 可进入开发：待确认 0 项，验收条款全部可测`
   - `⛔ 未就绪：待确认 N 项 / 不可测 M 条`

不要用「建议在开发前确认」这类模糊收尾——要么 0，要么列清单。
