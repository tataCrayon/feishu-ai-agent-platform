# 证据对照（代码 / 契约 / 会议）

你的价值在于**别让结论停留在纸面**。每条「与现状冲突」的结论必须有出处，没出处就不要下这个结论。

## 1. 从 PRD 抽检索词（不是从标题猜）

优先级从高到低：

1. 反引号包住的标识符（`` `order_status` ``）——那本来就是代码名；
2. 大写下划线枚举（`ORDER_STATUS`、`UN_SETTLED`）；
3. 中文专名（状态名、字段名、接口名、产品识别码前缀）；
4. 长度 ≥6 的英文小写标识符（`nativeExchangeRate`）。

**不要**拿「需求」「支持」「状态」这类泛词检索——命中全文等于没命中。

## 2. 检索与判读

用 `grep_codebase` 检索。**代码根是多仓的**（默认探测本仓同级的 webportal-bff（WebPortal BFF + RWA 引擎/代币化平台）/
hub-platform（中台）/ rwa-engine / wealth-service / webportal-admin / team-skills），回执的路径已带仓库名前缀
（`rwa-engine/flp-rwa-engine/...`）——判断证据属于哪个系统时以此为准。

需求横跨多个系统且某一个仓明显没被覆盖时，显式传 `roots=[...]` 缩小范围再查一次，
别反复用同一组词全量重试。

然后**逐个命中判读**：

| 现象 | 能得出什么结论 |
|---|---|
| 字段/枚举**存在且取值一致** | 可以写「与现有实现一致」——但只在确实看到定义处才写 |
| 字段/枚举**存在但取值不同** | `代码不一致`，必须给出 `文件:行号` |
| 只找到用法、找不到定义 | 只能说「未找到定义处」，**不能说「不存在」** |
| 一个都没命中 | 说「未检索到相关片段」，可能是别的仓库或别的命名；**先确认默认多根已覆盖该系统的仓** |

红线：

- **不推断实现**：代码片段里没出现的，不假设它存在或不存在。
- **不把「没搜到」当「没实现」**：不同仓库、不同命名、依赖包内实现都可能导致空结果。
- 只在看到**定义处**（枚举类、常量表、DDL、接口签名）时才下「冲突」结论；看到零散用法不算。

## 3. 上下游契约

- PRD 里跨系统的字段（推给 FinMix 的账户 ID、钱包地址等）要能对上对方的入参契约；对不上 → `口径冲突`。
- PRD 引用别的 PRD/文档时（`<cite>`），如果那份文档没读过，**明说没读**，不要默认它一致。
- 状态/枚举在两篇文档里各定义一次时，取差集并指出。

## 4. 会议结论

`read_conversation` 能看当前会话最近的讨论；会议纪要要从用户给的链接读（`ingest_meeting` 是整理链路，评审这里只需要读素材）。

判据：PRD 写的与会议结论冲突时，报 `口径冲突` 并同时给两处出处；会议里说「待定」而现在 PRD 写定了 → 标为「需确认是否已拍板」，不要当成已定。

## 输出格式

```
kind: 代码不一致 / 口径冲突
title: ≤30 字
quote: PRD 原文逐字引用（≤60 字）
section: 章节
issue: 冲突点（含代码出处 文件:行号）
suggestion: 改 PRD 还是改代码，两种方向都写一句，倾向哪个说清理由
evidence: 文件路径:行号 / 文档标题
```

`evidence` 为空时，这条结论降级为「待确认」，不要写成「代码不一致」。
