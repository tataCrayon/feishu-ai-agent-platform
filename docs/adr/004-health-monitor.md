# ADR-004：Agent 健康监控与自愈（AgentHealthMonitor）

> ADR 编号：`ADR-004` ｜ 状态：`已实现`（**实现范围比原设计窄**，见 §5「负面」）
> 创建 2026-08-14 ｜ 决策者 @devuser

## 1. 背景

推理层曾由多个独立的 cc-connect project 构成，每个 Agent 独占一个 Claude Code 会话。
任一个 Agent 崩溃或卡死，对应能力即**静默失效**——dispatch 只是超时返回，群里没有任何可靠性提示。
cc-connect 原生心跳（`HEARTBEAT.md`，60 分钟空闲触发）粒度太粗，且依赖 AI 处理，
无法满足分钟级可用性感知。

## 2. 决策考虑

- **触发因素**：多 Agent 拆分扩大故障面，单 Agent 失效无感知。
- **约束条件**：不引入 Prometheus / Grafana / Supervisor 等外部基础设施；单节点 Windows；
  探测必须避免污染真实用户会话上下文。
- **非目标**：不做进程级自愈；不做响应内容正确性检测。

## 3. 决策选项

### 选项 A：应用内 Python 周期巡检

- **描述**：`main.py` 起一个后台 asyncio 任务，每 300s 对每个启用的 Agent 发最小 ping，
  按响应延迟分级 green (<5s) / yellow (5–30s) / red (无响应)；状态写
  `logs/health/status.jsonl`（逐条）与 `current.json`（快照），连续失败 ≥3 次告警。
- **优点**：5 分钟粒度，比原生心跳快一个数量级，不依赖 AI；复用已有的同步通道；
  专用 `__health_check__` session key 隔离，不污染真实对话；文件输出与既有工具链衔接。
- **缺点与代价**：每次探测要起子进程 + 少量 token；`check_all()` 串行，
  单个 Agent 挂死时最坏阻塞 = timeout × Agent 数（120s × 4 ≈ 480s，会超周期）；
  只探测「能响应」，不检测内容正确性。
- **适用场景**：多 Agent 拆分后需要分钟级可用性感知的中小单机部署。

### 选项 B：扩展 cc-connect 原生心跳

- **优点**：免新增组件。
- **缺点与代价**：60 分钟粒度；`only_when_idle` 使忙碌期不被探测；高频探测要烧全量上下文 token；
  与维护任务强耦合，故障时审计记录混乱。
- **适用场景**：对故障感知延迟不敏感。

### 选项 C：独立监督守护进程（supervisor / systemd 风格）

- **优点**：进程级自愈能力最强。
- **缺点与代价**：Windows 下跨进程管理成本高；只覆盖「进程死」，不覆盖「进程活着但 Agent 卡死」；
  与现有启动链路职责重叠。
- **适用场景**：多机 / 容器化部署。

### 选项 D：什么都不做（依赖 `channel.on_error` + 用户反馈）

- **缺点与代价**：Agent 静默失效多数不抛异常（只是超时），用户完全无感知；故障排查回归人肉。
  与「可观测性」目标直接冲突，不可接受。

## 4. 决策结论

**选定：选项 A。**

- **核心理由**：① 5 分钟 vs 60 分钟，故障发现延迟降一个数量级且不依赖 AI；
  ② 零新组件、零会话污染、零外部依赖；③ 文件输出直接接既有工具链。
- **放弃其他选项**：B 粒度不够且与维护任务耦合；C 在单机且无进程自愈刚需时成本不划算；
  D 违背可观测性目标。
- **影响范围**：新增健康探测模块；`main.py` 启动接线 + 常驻循环；可观测层新增 `health` 日志；
  新增 `logs/health/`。

## 5. 后果

**正面**：分钟级故障感知；健康数据进可观测与周报；启动即初始快照，重启后可快速核对基线。

**负面 / 需接受**：
- **实现范围收窄**：原设计有 dead（进程不存在）级别与进程级自愈动作，实际只产出
  green/yellow/red，「自愈」= 告警日志，恢复动作保持人工——这是有意的（自动化恢复风险更大）。
  想要进程级恢复必须另立 ADR 决策。
- **串行探测会超周期**：单 Agent timeout=120s 时最坏 480s > 300s 周期。
  将来并发化（`asyncio.gather`）或减小单 Agent timeout 才能根治。
- 每周期有子进程 + token 开销，红/黄状态的 Agent 会因重试放大开销。

**必须配套的约束**：
1. 探测必须用独立 session key，禁止用真实用户会话 key（会污染对话上下文）。
2. 探测消息保持最小（一个 ping），禁止携带业务上下文。
3. 健康探测**不得向飞书群发消息**——静默探测，结果只落文件与日志。
