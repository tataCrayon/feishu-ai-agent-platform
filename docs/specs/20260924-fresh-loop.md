# 知识保鲜回路（流程 + 期望驱动存量修改）— 制度规格

> Spec ID：`SPEC-20260924-fresh-loop` ｜ 创建 2026-09-24
> 一句话主张：**把「为什么」的载体从 git log 升级为带证据锚点的文档页，
> 把「改完不更新文档」从习惯问题变成工作流红灯。**

## 一、要解决的问题

工程体量变大后，改一个功能要先回答三件事：为什么当初这么写、现在为什么是这个形态、
下一步该往哪走。每次修改都靠 git 考古，成本高且容易踩进历史事故的暗坑。

**体检结论（2026-09-24）**：本仓库已具备该能力的约 80%——「为什么」有 ADR + commit message，
「是什么」有 project-index + CLAUDE.md，「要什么」有 golden 双层门禁。
真实缺口不是缺失而是**腐化**：索引与代码脱节、历史认知散在 commit 里没有锚点。

## 二、用户操作时序

```gherkin
actor: 开发者（人类或 AI 会话）
goal: 在不理解实现细节的前提下，正确完成一次功能修改

场景: 冷启动修改闭环
1. Given 只知道功能名与期望效果
   When  打开 docs/features/{域名}.md
   Then  [用户看到] 一页纸给出：主链路（文件:符号级）、期望行为、
         不变量（带证据锚点）、单源与「不改」边界、已知坑

2. When  按简报指认的单源文件实施修改
   Then  [用户看到] 修改落在简报指认的位置；触到「不改」边界时停下提问
         而不是自信越界

3. When  修改完成提交
   Then  [用户看到] 同一 commit 里带 project-index 行更新 + 简报证据锚点 + Docs: 行

场景: 发现文档腐化
1. Given 简报与代码矛盾
   When  按「以代码 + commit 为准」处理
   Then  [用户看到] 同一个 commit 里回写简报，而不是留一条「待更新」
```

## 三、需求与验收

### R1 功能简报体系

高频改动域各一页「薄规格」，**粒度上限一页**，八节结构见 `_feature-brief-template.md`。

**不变量**

- R1-1 每条不变量必须带证据锚点（commit hash / ADR 编号 / 事故日期）；无锚点的降级为「建议」。
- R1-2 简报与代码矛盾 → 以代码 + commit 为准，并在同一 commit 回写简报。
- R1-3 简报不是 spec 重骨架，只写「改这个功能需要知道的最小集合」。

- **AC1** 高频域简报 ≥3 份，每份八节齐全且不变量带锚点（现状 9 份，见 `docs/README.md`）

### R2 改动收尾钩子

CLAUDE.md「改动收尾」四步，与代码同 commit：

1. **索引行同步**：行为变更 → 更新 `project-index.md` 对应行，行尾 `(YYYY-MM-DD)`
2. **证据锚点**：结构性决策 → 对应简报第 6 节补一行（日期 + 事件 + hash）
3. **commit `Docs:` 行**：正文末尾列本次更新的文档；无文档更新写 `Docs: 无（纯实现内聚改动）`
4. **简报优先**：该域有简报页就同步；新功能属高频域顺手建页

**红灯自检**：说不清「本次改了哪些文档行」= 没改完。

**不变量**

- R2-1 文档同步与代码改动**同 commit**——禁止「回头再补」，补不完的债就是腐化的起点。
- R2-2 不引入独立文档检查 CI；保鲜靠 commit 纪律 + `Docs:` 行可追溯。

- **AC2** `project-index.md` 含收尾保鲜条目
- **AC3** `CLAUDE.md` 含「改动收尾」段（四步 + 红灯自检）

### R4 演练验证（spec-driven 修改实验）

用真实小改动验证核心主张：**只凭简报 + 期望效果，不预读实现，一次通过**。
结果记入简报页第 8 节（日期 / 需求 / 是否未预读 / 一次通过 / 返工原因）。

**放弃信号（防沉没成本）**：若两次演练中简报驱动的返工都明显多于直接读代码改，
或每份简报都必须先读懂实现才写得出来——停掉这套投入，退回「AI 现场读代码 + git 考古」，
只保留 golden 门禁与 commit 纪律。

## 四、范围外

- 不引入 spec-kit 等外部工作流工具（面向 from-scratch 新功能，本痛点在存量维护）。
- 不为全部功能域补文档，只做高频域起步。
- 不动 `.agent/memories/`（服务机器人运行，不服务开发者）。
- 不建文档自动校验 CI。
